## Why

管理员要在控制台看「大家拿机器人主要做什么（大类）」「各项能力用得怎么样」「谁连续失败、谁卡住了需要帮忙」。现在的心跳只有设备状态和出错记录（c2）：出错记录只有失败、没有成功，算不出「连续」；也没有任何用量。

控制台多收任何一类数据都要升采集清单版本。c3 只比 c2 多了用量统计（代号和数字），管理员定为小迭代：c2 的机器直接升，不再逐人确认（同事大多不碰终端）。

## What Changes

- 新采集清单 `c3`（比 c2 多「用量统计」）；新入网默认 c3。
- 本机给每张单归一个大类（7 个写死的代号），主会话派单时用 `ticket new --cat` 给，没给时本机按关键词判断。只存代号。
- 按过程日志记 worker 调用控制台下发的技能脚本：用了几次、成没成、失败归类码（只从退出码推）。技能包不用改。
- 心跳多一个 `usage`（只在本机清单是 c3 时带）：最近两天每天各大类的单数和做成数、各能力的次数 / 成功 / 失败归类码、最近连续没做成几单、正在跑的单最久几分钟没有新动作。
- c2 → c3 直接升级：本机清单是 c2 的，守护进程心跳前静默换成 c3（不私信）；只升一次，本人用 `ticket console accept c2` 退回后不再动。c1 不自动升。
- 控制台退回旧版本、不认识 `usage` 时，去掉它照报设备状态（和 `problems` 的处理一样）。

## Impact

- 规格：`docs/spec.md` §12 加「调整（add-usage-report）」。
- 代码：`ticketd/usage.py`（新）、`console.py`、`core.py`、`cli.py`、`scheduler.py`、`db.py`（tickets.cat、cap_calls 表）、`workspace/CLAUDE.md.tmpl`。
- 控制台：要先上线认识 c3 和 `usage` 的版本（控制台仓库 add-oversight），再发这一版 Larkyard；否则新入网会被拒（控制台不认识 c3）。
