## Purpose

让发布者在自己的电脑上，从一个 git tag 打出可验证的版本包和签名清单，使客户端只凭本机信任的公钥就能判断一个版本是不是发布者本人发的、内容有没有被改过、是不是一份被重放的旧清单。更新源（包括以后的控制台）没有私钥，只能发布或撤下发布者签好的文件。

## ADDED Requirements

### Requirement: 从 git tag 打出可复现的版本包
发版工具 SHALL 只从一个已存在的 git tag 打包，包内只含该 tag 下被 git 跟踪的文件，文件名为 `larkyard-<版本>.tar.gz`。工作树有未提交改动、tag 不存在、或 tag 指向的代码里 `ticketd/__init__.py` 的版本号与 tag 不一致时，发版工具 MUST 拒绝打包并说明原因。

#### Scenario: 正常打包
- **WHEN** 发布者对已存在的 tag `v0.3.0` 执行打包，且该 tag 里的 `__version__` 为 `0.3.0`
- **THEN** 生成 `larkyard-0.3.0.tar.gz`，包内只有该 tag 下被跟踪的文件，不含 `.git/`、未跟踪文件和本机配置

#### Scenario: 版本号不一致
- **WHEN** tag 为 `v0.3.0`，但该 tag 里的 `__version__` 为 `0.2.0`
- **THEN** 发版工具退出码非 0，提示版本号与 tag 不一致，不生成任何文件

#### Scenario: 同一个 tag 打两次
- **WHEN** 对同一个 tag 在同一台机器上打包两次
- **THEN** 两次得到的包 SHA-256 相同

### Requirement: 版本清单和递增序号
每份清单 SHALL 是确定的 UTF-8 JSON（键排序、无多余空白），签名针对这份文件的原始字节。清单至少包含：格式版本、产品名、类型（`release` / `rollback` / `rekey`）、版本号、包文件名、包的 SHA-256、包大小、通道、最低可升级起点版本、git 提交号、签名时间、序号 `seq`、更新说明。`seq` 是发版工具在发布者本机维护的计数器，每签一份清单加一，MUST 严格递增，发版工具 MUST NOT 签出小于等于本机已用过的序号。

#### Scenario: 清单字段完整
- **WHEN** 发布者为 `0.3.0` 生成通道 `canary` 的清单
- **THEN** 清单包含上面列出的全部必需字段，`sha256` 与包文件实际的 SHA-256 一致，`commit` 与 tag 指向的提交一致，`seq` 比上一份签出的清单大

#### Scenario: 计数器被回拨
- **WHEN** 本机计数器文件被改成比已用过的最大序号还小
- **THEN** 发版工具拒绝签名并提示序号回退（已用过的最大序号另外记在签名日志里核对）

### Requirement: 一次发版签齐所有通道
发版工具 SHALL 在一次发版中为同一个版本包分别生成并签好 `canary`、`early`、`stable` 三份清单（通道字段不同，各自有序号）。「推进到下一个通道」只是发布那份已经签好的清单，更新源 MUST NOT 需要私钥。

#### Scenario: 推进不需要重签
- **WHEN** 发布者发 `0.3.0`，之后要把它从 `canary` 推进到 `stable`
- **THEN** 只需把发版时已签好的 `stable` 清单放到更新源的 `stable` 通道，不需要再次签名

### Requirement: 用发布者本机的 Ed25519 主密钥签名
发版工具 SHALL 用 `ssh-keygen -Y sign` 和发布者指定的 Ed25519 主私钥签名，签名命名空间固定为 `larkyard-release`，每份清单输出对应的 `.sig`。发版工具 MUST NOT 把私钥写入仓库、版本包、清单或任何日志，也 MUST NOT 提供在服务器上签名的模式。非 Ed25519 的密钥 MUST 被拒绝。

#### Scenario: 签名成功
- **WHEN** 发布者用自己的 Ed25519 主私钥签 `0.3.0` 的清单
- **THEN** 生成 `.sig`，用对应公钥和命名空间 `larkyard-release` 执行 `ssh-keygen -Y verify` 通过

#### Scenario: 用错误的密钥类型
- **WHEN** 发布者指定一把 RSA 私钥签名
- **THEN** 发版工具退出码非 0，提示只接受 Ed25519，不生成签名

### Requirement: 有有效期的回滚清单
发版工具 SHALL 能为一个已发布的旧版本生成类型为 `rollback` 的清单：包信息与那个旧版本一致，带新的序号和 `expires_at`（默认签名后 72 小时，最长 7 天），由主密钥签名。只有类型为 `rollback`、且在有效期内的清单才允许客户端装回更低的版本。

#### Scenario: 生成回滚清单
- **WHEN** 当前已发布 `0.3.0`，发布者为旧版本 `0.2.1` 生成通道 `stable` 的回滚清单
- **THEN** 得到一份类型 `rollback`、版本 `0.2.1`、`expires_at` 为 72 小时后、序号比之前都大的清单和它的签名，旧包文件不需要重新打

#### Scenario: 有效期超限
- **WHEN** 发布者要求回滚清单有效期为 30 天
- **THEN** 发版工具拒绝，提示最长 7 天

### Requirement: 预签的暂停标记
发版工具 SHALL 能一次签出一批暂停标记，每个标记带 `not_before` 和 `not_after`，覆盖一个不超过 7 天的时间窗口，多个窗口首尾相接（默认连续 12 周）。暂停标记由主密钥签名。更新源发布当前窗口的那一份，就能让客户端停止安装，不需要私钥。

#### Scenario: 一批暂停标记
- **WHEN** 发布者执行「签 12 周暂停标记」
- **THEN** 得到 12 个标记，各自窗口 7 天、首尾相接、互不重叠，都能用主公钥验过

### Requirement: 离线备份密钥负责换钥
信任关系 SHALL 包含两把不同的 Ed25519 公钥：主公钥（验普通清单、回滚清单、暂停标记）和离线备份公钥（只验换钥清单）。换钥清单（类型 `rekey`）带新的主公钥、它要替换的旧主公钥、序号和签名时间，MUST 由离线备份私钥签名；主私钥签的换钥清单 MUST 被视为无效。

#### Scenario: 主密钥泄露后换钥
- **WHEN** 主私钥泄露，发布者用离线备份私钥签发一份带新主公钥的换钥清单
- **THEN** 该清单能用备份公钥验过、写明被替换的是泄露的那把旧主公钥；用泄露的主私钥签出的换钥清单验不过
